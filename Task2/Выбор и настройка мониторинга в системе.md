# Выбор и настройка мониторинга в системе

## 1. Система и C4-диаграмма в контексте мониторинга

В системе три приложения и общая инфраструктура:

- **Онлайн-магазин** (Vue + Spring Boot, Shop DB, S3) — B2C-заказы;
- **CRM** (Vue + Spring Boot, общая Shop DB) — продавцы, подтверждение и статусы заказа;
- **MES** (React + C#, MES DB) — производство и расчёт цены;
- **RabbitMQ** — интеграция CRM ↔ MES;
- **EC2** (по одному инстансу на приложение), managed PostgreSQL, S3, балансировщик.

Яндекс Метрика покрывает только **браузер B2C-клиента**. Она не видит API-партнёров, backend, БД, RabbitMQ, CRM, MES, SLA и внутренние ошибки. Слепые зоны: потеря заказа между системами, зависание в статусе, очередь расчёта цены, деградация ресурсов и отсутствие раннего оповещения.

## 2. Мотивация

Мониторинг нужен, чтобы управлять потерями, а не узнавать о них из жалоб:

- **вернуть потерянные заказы** — жалобы API-партнёров и потерянные контракты видны в метриках за минуты;
- **выполнять SLA 3 недели** — время в каждом статусе показывает, где заказ стоит;
- **быстрее находить инциденты** — алерты по ошибкам, latency и очередям вместо ручного разбора;
- **сократить MTTR** — трейсинг и метрики показывают место сбоя;
- **быть готовыми к росту и API-контрактам** — данные о нагрузке и ёмкости;
- **обосновывать расходы** — утилизация ресурсов вместо интуиции;
- **проверять эффект изменений** — измеримые «до/после» для инициатив.

Экономия на первом предотвращённом крупном контракте и сокращении простоя перекрывает затраты на мониторинг.

## 3. Выбор подхода к мониторингу

| Часть системы | Подход | Почему |
|---|---|---|
| Shop API, CRM API, MES API, B2B API | **RED** (Rate, Errors, Duration) | Синхронные запросы: важны RPS, доля ошибок и latency |
| EC2, PostgreSQL, RabbitMQ, S3, балансировщик | **USE** (Utilization, Saturation, Errors) | Ресурсы с ёмкостью и насыщением |
| Конвейер заказа, фронтенды, потребители RabbitMQ | **Четыре золотых сигнала** (Latency, Traffic, Errors, Saturation) | Сквозные и асинхронные сценарии, не привязанные к HTTP |

## 4. Метрики по частям системы

### 4.1. API: Shop, CRM, MES

| Метрика | Зачем | Ярлыки |
|---|---|---|
| RPS | Нагрузка и тренд, вход для алертов (RED: Rate) | `service`, `route`, `method`, `status_code`, `channel` |
| RPS per user (MES API) | Выявить партнёра, который флудит; основа rate-limit | `partner_id`, `endpoint`, `channel` |
| CPU % | Утилизация CPU, риск роста latency (USE) | `instance`, `service`, `environment` |
| Memory Utilisation | Риск OOM и утечек | `instance`, `service`, `environment` |
| Response time (latency) | Скорость ответа, p50/p95/p99 (RED: Duration) | `service`, `route`, `method`, `status_code` |
| HTTP 200 / HTTP 500 | Доля успешных и серверных ошибок (RED: Errors) | `service`, `route`, `method`, `status_code`, `channel` |
| Simultaneous sessions | Активная аудитория и фактическая нагрузка | `channel`, `role`, `device_type` |
| KB received / KB sent | Входящий и исходящий трафик, аномалии и стоимость | `service`, `route`, `direction` |

> HTTP 200 и 500 — срезы одной метрики `http_server_requests_total` по `status_code`. RPS per user для Shop и CRM не беру: у B2C нет аутентификации, у CRM единицы пользователей — разрез не оправдывает кардинальность.

### 4.2. Базы данных: Shop DB, MES DB

| Метрика | Зачем | Ярлыки |
|---|---|---|
| Memory Utilisation | Насыщение памяти PostgreSQL, риск роста latency (USE) | `instance`, `database` |
| Number of connections | Приближение к `max_connections` — риск отказа | `instance`, `database`, `state` |
| Size of DB instance | Рост БД и планирование диска | `instance`, `database` |

### 4.3. RabbitMQ

| Метрика | Зачем | Ярлыки |
|---|---|---|
| Number of dead-letter-exchange letters | Сообщения в DLX — уже потерянные или отложенные заказы | `queue`, `vhost`, `exchange` |
| Number of messages in flight | Неподтверждённые сообщения: зависшие или медленные потребители (USE) | `queue`, `vhost`, `consumer` |
| Queue depth / message age | Очередь и реальное время ожидания заказа | `queue`, `vhost` |
| Queue consumers | 0 потребителей — очередь никто не разбирает | `queue`, `vhost` |

### 4.4. S3

| Метрика | Зачем | Ярлыки |
|---|---|---|
| Size of S3 storage | Рост хранилища 3D-моделей, планирование затрат | `bucket`, `storage_class` |
| Errors / request duration | Ошибки и задержки чтения и записи моделей | `bucket`, `operation`, `status_code` |

### 4.5. Дополнительные метрики (сверх списка)

| Метрика | Зачем | Ярлыки |
|---|---|---|
| `price_calculation_duration_seconds` | Расчёт цены 2–3 мин (до 30): p95/p99 и таймауты | `complexity`, `result` |
| `price_calculation_queue_depth` / `age` | Очередь расчётов — главный затор конвейера | `priority`, `complexity` |
| `order_status_age_seconds` | Время заказа в статусе — контроль SLA | `status`, `channel` |
| `orders_stuck_total` / `order_sla_compliance_ratio` | Зависшие заказы и доля закрытых за 3 недели | `status`, `channel`, `partner_tier` |
| `order_event_failures_total` / `duplicates_total` | Потери и дубли событий в конвейере | `event_type`, `consumer`, `reason` |
| `b2b_orders_accepted_total` / `created_total` | Сверка «приняли / создали» — детектор потери партнёрских заказов | `partner_id` |
| `b2b_rate_limited_total` / `auth_failures_total` | Отказы по лимитам и проблемы с ключами | `partner_id`, `reason` |
| `pg_slow_queries_total` / `pg_locks_count` / `pg_deadlocks_total` | Медленные запросы и блокировки — причина деградации API | `instance`, `database`, `operation` |
| `alb_http_5xx_total` / `alb_unhealthy_hosts` | Ошибки и здоровье инстансов на входе в систему | `service`, `target_group` |
| `web_vitals_lcp_seconds` / `js_errors_total` | Скорость и стабильность сайта и 3D-редактора | `page`, `device_type`, `release` |

**Правила ярлыков:** только ограниченные значения (`service`, `route`-шаблон, `status_code`, `channel`, `queue`, `status`, `partner_id`). Запрещены `user_id`, `order_id`, `trace_id`, сырые URL и текст ошибок — они остаются в логах и трейсах.

## 5. Показатели насыщенности и пороги (доп. задание)

| Показатель | Порог | Почему | Действие |
|---|---|---|---|
| CPU % | > 80% 10 мин | 20% запаса на пики и GC | P2-алерт; добавить инстанс / масштабировать |
| Memory | > 85% | Запас до OOM и пауз GC | P2-алерт; проверить утечки, масштабировать |
| Connections БД | > 80% `max_connections` | Остаток нужен служебным подключениям | P1; проверить пулы, PgBouncer, поднять лимит |
| Диск БД | > 80% | Запас на WAL и рост | P2-тикет на расширение; при 90% — P1 |
| Messages in flight | > 1 000 или рост 15 мин | Потребители не успевают | P2; добавить consumer'ов |
| Глубина очереди | > 1 000 или рост 15 мин | Очередь разбирается медленнее пополнения | P2; масштабировать потребителей |
| Возраст сообщения | > 5 мин | Расчёт занимает 2–3 мин, 5 мин — отклонение | P1 при > 15 мин; страница on-call |
| DLX | > 0 | Любое сообщение — потерянный заказ | P1; страница on-call, ручной разбор |
| Error rate 5xx | > 1% за 5 мин | Заметная доля отказов для клиентов | P1; страница on-call |
| Latency p95 | > 1 с 10 мин | Вдвое выше целевых 500 мс | P2; при росте ошибок — P1 |
| S3 throttling / errors | > 0 throttle / > 1% ошибок | Ломается загрузка и чтение моделей | P2; увеличить квоту, проверить ретраи |
| Unhealthy hosts | > 0 | Инстанс уже вне работы | P1; вывести из балансировки, разобрать |

Пороги стартовые, калибруются после нагрузочного тестирования. P1 — звонок дежурному, P2 — сообщение и тикет, P3 — только дашборд.

## 6. План действий

1. Развернуть **Prometheus** (time-series БД) + **Grafana** + **Alertmanager**; логи — **Loki**, трейсы — **OpenTelemetry + Tempo/Jaeger**.
2. Настроить retention и резервное копирование метрик.
3. Подключить экспортеры: `node_exporter`, `postgres_exporter`, `rabbitmq_prometheus`, CloudWatch для S3 и балансировщика.
4. Инструментировать сервисы: Spring Boot — Micrometer, C# — OpenTelemetry .NET, фронтенд — RUM/web-vitals.
5. Зафиксировать соглашения по именам метрик, ярлыкам и `trace_id`.
6. Собрать дашборды: по сервисам, инфраструктуре, RabbitMQ, конвейеру заказа и B2B-партнёрам.
7. Настроить алерты и SLO по порогам из раздела 5, привязать runbook'и и дежурство.
8. Провести нагрузочное тестирование и откалибровать пороги.
9. Задокументировать доступы, стоимость и процесс изменения мониторинга.
