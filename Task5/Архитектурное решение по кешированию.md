# Архитектурное решение по кешированию

## 1. Контекст

Дашборд оператора в MES — это список заказов с фильтром по статусу, сортировкой «новые сверху», пагинацией и счётчиками. Каждое открытие страницы выполняет несколько тяжёлых запросов к MES DB: `JOIN`, `COUNT`, сортировку и выборку страницы. База одна для чтения и записи, реплик нет, а одни и те же первые страницы одновременно запрашивают все операторы.

Скорость выполнения заказа складывается из двух частей. Расчёт цены занимает 2–3 минуты (до 30 на сложных моделях) — кеширование его не ускорит, для этого нужны асинхронные воркеры. А вот ожидание списка, карточки и статуса — это чтение, которое кеш ускоряет и разгружает БД. Поэтому кешируем read-heavy часть MES-контура; запись статусов и расчёт цены остаются в БД как в источнике правды.

## 2. Мотивация

Кеширование нужно, чтобы:

- убрать повторяющиеся одинаковые чтения первых страниц списка;
- снизить нагрузку на MES DB и освободить соединения и CPU для записи статусов и расчёта цены;
- выдержать пики при открытии смены и массовом обновлении страниц;
- быстрее отдавать статус операторам и API-партнёрам;
- перестать перечитывать справочники и прайс-правила на каждом запросе.

### 2.1. Что включаем в кеширование

| Элемент | Кешируем | Почему |
|---|---|---|
| Список заказов (первые 5 страниц по статусам) | **Да** | Самый частый и повторяемый запрос; данные меняются реже, чем читаются |
| Карточка заказа по `order.id` | **Да** | Постоянные переходы «список → карточка → назад» |
| Счётчики по статусам | **Да** | Дорогой `COUNT` на каждой странице; отставание в десятки секунд допустимо |
| Справочники: статусы, приоритеты, материалы | **Да** | Меняются редко, читаются постоянно |
| Прайс-правила и материалы для расчёта цены | **Да, с версией** | Убирают повторные чтения из БД в каждом расчёте |
| Результат расчёта цены по 3D-модели | **Нет** | Модели уникальны, hit rate низкий, устаревшая цена опаснее задержки |
| Запись статуса и история переходов | **Нет** | Транзакционная операция, источник правды — БД |
| Персональные данные клиента | **Нет** | Кеш не должен расширять поверхность утечки |

Кеширование не заменяет индекс `(status, created_at)`, keyset-пагинацию и асинхронный расчёт цены: сначала убираем худшие запросы, затем ставим кеш сверху.

## 3. Предлагаемое решение

### 3.1. Серверное кеширование

Основное решение — **серверный кеш в MES API на Redis**. Клиентское кеширование используется только как дополнение.

Почему серверное:

- общий кеш для всех операторов и API-партнёров, а не персональный кеш браузера;
- централизованная инвалидация после смены статуса;
- только серверный кеш уменьшает число запросов к PostgreSQL;
- одинаковое поведение на всех инстансах MES API.

Почему не только клиентское:

- первый заход всегда холодный и создаёт нагрузку на БД;
- кеш браузера нельзя надёжно инвалидировать с сервера;
- разные операторы не переиспользуют данные друг друга;
- API-партнёры не работают с браузерным кешем.

Дополнительно на клиенте: React Query с `staleTime` 10–15 с убирает повторные запросы при переходах, `ETag`/`Cache-Control` экономят трафик, статика кешируется в CDN. Источником правды клиентский кеш не является.

### 3.2. Паттерн кеширования: Cache-Aside

Выбран **Cache-Aside (lazy loading)**:

1. MES API читает ключ из Redis.
2. При попадании возвращает значение.
3. При промахе читает MES DB, кладёт результат в Redis с TTL и возвращает ответ.
4. При смене статуса сначала коммитит транзакцию в БД, затем инвалидирует кеш.
5. Если Redis недоступен, API работает напрямую с БД — медленнее, но без потери данных.

Почему он:

- списки читаются постоянно, статусы меняются редко — lazy-заполнение кеширует только то, что реально запросили;
- инвалидация простая: удалить карточку и увеличить версию списков;
- падение Redis не блокирует запись статусов и не роняет API;
- в кеш не попадают данные, которые никто не прочитает.

| Критерий | Cache-Aside (выбран) | Write-Through | Refresh-Ahead |
|---|---|---|---|
| Запись | БД + инвалидация | БД + кеш синхронно | БД + фоновое обновление |
| Консистентность | TTL + инвалидация | Выше при успехе, но риск расхождения | Средняя: фон может отдать устаревшее |
| Сложность | Низкая | Средняя | Высокая |
| Наш профиль нагрузки | Подходит | Избыточен | Избыточен |

**Почему не Write-Through.** Смена статуса — транзакционная и редкая операция. Синхронная запись в кеш добавляет вторую точку отказа и задержку в критический путь, а при сбое одной из записей появляется расхождение, которое сложнее разбирать, чем удаление ключа.

**Почему не Refresh-Ahead.** Нужны предсказуемые горячие ключи, а у нас ключи комбинаторные: статус × курсор × лимит. Фоновое обновление создаёт лишнюю нагрузку на БД и всё равно не гарантирует свежесть после записи — инвалидация по событию остаётся нужна.

### 3.3. Диаграмма последовательности

[Диаграмма последовательности кеширования](Sequence-кеширование.drawio)

Участники: **Оператор**, **MES SPA**, **MES API**, **Redis**, **MES DB**, **RabbitMQ**, **CRM API**.

На диаграмме два сценария:

- **чтение списка** — `GET` списка, проверка ключа в Redis, исходы `HIT` и `MISS`, запрос `SELECT ... ORDER BY created_at DESC LIMIT 50` при промахе и запись `SETEX` с TTL;
- **изменение статуса** — `UPDATE orders` + `INSERT status_history`, затем `DEL` карточки и `INCR` версии списков после коммита, публикация `order.status_changed` и ответ оператору.

Если статус приходит из CRM событием, MES-потребитель обновляет БД идемпотентно и выполняет ту же инвалидацию.

### 3.4. Стратегия инвалидации

Используем **программную инвалидацию по ключу + версионирование ключей + TTL как страховку**.

| Объект | Ключ и TTL | Инвалидация |
|---|---|---|
| Карточка заказа | `mes:order:{orderId}:v{orderVersion}`, 5 мин | Новая версия после изменения + `DEL` старого ключа |
| Список заказов | `mes:orders:v{catalogVersion}:status:{status}:limit:{n}:cursor:{cursor}`, 45 с | `INCR` версии |
| Счётчики по статусам | `mes:orderstats:v{catalogVersion}`, 45 с | `INCR` версии |
| Справочники и прайс | `mes:dict:statuses:v{dictVersion}`, `mes:pricing:v{pricingVersion}`, 1 ч | Версия при обновлении |

1. **Программная инвалидация после коммита.** При смене статуса MES API удаляет карточку, увеличивает версию списков и публикует событие. Инвалидация выполняется только после успешного `COMMIT`, иначе можно удалить кеш, а транзакция откатится.
2. **Версионирование ключей.** Версия в ключе обесценивает все варианты списка (статус × курсор × лимит) одной операцией `INCR`, без `KEYS`/`SCAN`. Старые ключи доживают TTL.
3. **TTL как страховка.** Если инвалидация потерялась, устаревшая запись живёт не дольше TTL: 45 с для списков и счётчиков, 5 минут для карточки, 1 час для справочников.

Почему не подходят другие стратегии:

| Стратегия | Почему не подходит |
|---|---|
| Временная (только TTL) | Статус может быть устаревшим до 5 минут; оператор увидит неверный статус |
| По ключу (только `DEL`) | Ключей списка слишком много, их нельзя надёжно перечислить; `KEYS` блокирует Redis, `SCAN` дорог |
| Write-through (обновление кеша при каждой записи) | Синхронная запись в кеш увеличивает latency и риск расхождения при сбое |
| Фоновая пересборка по расписанию | То же, что TTL, но менее предсказуемо: после смены статуса данные всё равно устареют на минуты |

Итоговая согласованность — eventual: обычно 1–2 секунды, в худшем случае — TTL. Для чтений, где нужна строгая свежесть, можно обойти кеш флагом `?consistent=true`.
