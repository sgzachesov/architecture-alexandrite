# Архитектурное решение по логированию

## 1. Система и C4-диаграмма в контексте логирования

Заказ проходит через три приложения, две базы, RabbitMQ и S3. Сейчас каждое приложение пишет логи в свой файл, формат и состав полей не согласованы, а `trace_id` и `order.id` в записях отсутствуют. Из-за этого разбор начинается со слов клиента и ручного сопоставления файлов на разных серверах.

### 1.1. Откуда собираем логи

На C4-диаграмме системы, логи которых собираются, выделены **красной пунктирной рамкой**:

| Система | Какие логи | Зачем |
|---|---|---|
| Онлайн-магазин (Frontend) | Ошибки JS, ошибки загрузки 3D-редактора, действия оформления заказа | Понять, что видел пользователь до обращения |
| Shop API (Spring Boot) | HTTP-запросы, создание заказа, загрузка в S3, ошибки | Основная точка входа B2C-заказов |
| CRM (Frontend) | Ошибки интерфейса, действия продавца | Разбор ручных операций подтверждения |
| CRM API (Spring Boot) | Подтверждение заказа, смена статусов, публикация событий | Узел, где заказ передаётся в производство |
| MES (Frontend) | Ошибки дашборда, действия оператора, зависания | Проблемы операторов и медленного дашборда |
| MES API (C#) | Приём заказа, расчёт цены, работа с БД и S3, статусы | Самый долгий и рискованный участок конвейера |
| RabbitMQ | Подключения, публикация/доставка, DLQ, ошибки потребителей | Потеря и дубли сообщений |
| Shop DB / MES DB (PostgreSQL) | Медленные запросы, ошибки, блокировки, подключения | Первопричина деградации API |
| S3 | Access-логи: чтение и запись 3D-моделей | Ошибки загрузки и чтения моделей |

Схема: [C4-диаграмма сбора логов](C4-логирование.drawio). Красным на ней выделены новые компоненты и связи, красной пунктирной рамкой — системы, откуда собираются логи.

## 2. Список логов уровня INFO

INFO — основной уровень production: бизнес-события, доступ к API и жизненный цикл сервиса. Каждая запись — JSON с обязательными полями:

`timestamp` (ISO 8601, UTC), `level`, `service`, `environment`, `version`, `trace_id`, `span_id`, `event`, `message`.

Дополнительно для заказов: `order.id`, `order.number`, `order.status`, `order.channel`, `partner.id`, `customer_id_hash`.

| Событие | Обязательные поля |
|---|---|
| `order.created` | `order.id`, `order.number`, `channel`, `partner.id`, `customer_id_hash`, `amount`, `items_count`, `status=INITIATED`, `trace_id` |
| `order.file_uploaded` | `order.id`, `file.id`, `file.size_bytes`, `file.content_type`, `storage.bucket`, `duration_ms`, `result` |
| `order.submitted` | `order.id`, `from_status=INITIATED`, `to_status=SUBMITTED`, `duration_in_prev_status_ms`, `source` |
| `order.received_by_crm` | `order.id`, `source`, `received_at`, `trace_id` |
| `order.confirmed` | `order.id`, `from_status=SUBMITTED`, `to_status=MANUFACTURING_APPROVED`, `initiator_role`, `duration_in_prev_status_ms` |
| `price.calculation_started` | `order.id`, `calculation_id`, `model_complexity`, `attempt`, `queue_wait_ms` |
| `price.calculation_finished` | `order.id`, `calculation_id`, `duration_ms`, `result`, `price` |
| `order.status_changed` | `order.id`, `from_status`, `to_status`, `initiator` (system/user role), `duration_in_prev_status_ms`, `trace_id` |
| `order.assigned` | `order.id`, `operator_id_hash`, `priority`, `assignment_delay_ms` |
| `manufacturing.started` | `order.id`, `started_at`, `operator_id_hash` |
| `manufacturing.completed` | `order.id`, `completed_at`, `duration_ms` |
| `order.shipped` | `order.id`, `shipped_at`, `delivery_type` |
| `order.closed` | `order.id`, `closed_at`, `cycle_time_ms`, `sla_met` |
| `http.request` | `http.method`, `http.route`, `http.status_code`, `duration_ms`, `channel`, `partner.id`, `trace_id` |
| `integration.publish` / `integration.consume` | `queue`, `event_type`, `message_id`, `order.id`, `result`, `retry_count`, `trace_id` |
| `s3.request` | `operation` (GetObject/PutObject), `bucket`, `file.id`, `duration_ms`, `status_code` |
| `db.slow_query` | `db.operation`, `db.table`, `duration_ms`, `rows_affected` (без текста SQL и параметров) |
| `auth.login` | `user_id_hash`, `role`, `result`, `ip_truncated` |
| `service.started` | `version`, `environment`, `config_hash`, `started_at` |
| `scheduled_job` | `job_name`, `duration_ms`, `result` |

### 2.1. Другие уровни логирования

| Уровень | Когда используем | Где |
|---|---|---|
| **TRACE** | Пошаговая отладка алгоритмов, только локально | dev, в prod выключен |
| **DEBUG** | Детали обработки, временно включается для разбора инцидента | dev/release всегда; prod — точечно и с TTL |
| **INFO** | Бизнес-события, HTTP-доступ, запуск/остановка, интеграции | prod по умолчанию |
| **WARN** | Восстановимые отклонения: ретрай, 4xx-валидация, медленный запрос, рост очереди, неудачный логин | prod |
| **ERROR** | Операция не выполнена: 5xx, ошибка интеграции, сбой расчёта цены, недоступность БД | prod, алерт |
| **FATAL** | Сервис не может стартовать или есть риск потери данных | prod, немедленный алерт |
| **AUDIT** | Действия пользователей и доступ к чувствительным данным, отдельный неизменяемый поток | prod, отдельный тенант audit |

Правило: в prod не логируем DEBUG/TRACE постоянно — это дорого и повышает риск утечки данных. Включаем на время разбора через конфигурацию с автоматическим отключением.

## 3. Мотивация

Логирование нужно, чтобы разбор проблемы начинался с фактов, а не с пересказа клиента. Одна структурированная запись с `order.id`, `trace_id` и статусом позволяет за минуту ответить: что произошло, в каком сервисе, когда и с каким результатом.

### 3.1. Что это даёт компании

- **Снижение нагрузки на поддержку.** Типовые вопросы «где мой заказ» закрываются поиском по номеру, без привлечения разработчика.
- **Быстрый разбор инцидентов.** Вместо чтения логов на трёх серверах — единый поиск по `trace_id`/`order.id`.
- **Видимость потерь и зависаний.** События статусов и интеграций показывают, где заказ остановился.
- **Доказательная база.** Логи фиксируют, что именно произошло, — это снижает споры с партнёрами и помогает в разборе SLA.
- **Безопасность и аудит.** Видны входы, смены статусов и доступ к данным.
- **Основа для алертинга и аномалий.** По логам можно замечать всплески ошибок и подозрительную активность.

### 3.2. Метрики, на которые повлияет внедрение

**Технические:**

| Метрика | Как измеряем | Целевой эффект |
|---|---|---|
| MTTR / время до root cause | Время от обращения до найденной причины | Снижение на 40–50% |
| Время поиска заказа по номеру | Время от запроса до найденной истории | < 1 минуты вместо десятков минут |
| Доля сервисов с согласованными логами | Сервисы с JSON и `trace_id` / все сервисы | 100% для заказного контура |
| Доля инцидентов, разобранных без разработчика | Обращения, закрытые поддержкой | Рост на 30–50% |

**Бизнес-метрики:**

| Метрика | Как измеряем | Целевой эффект |
|---|---|---|
| Обращения в поддержку на 100 заказов | Тикеты / заказы | Снижение на 30% |
| Доля заказов, уложившихся в SLA 3 недели | `order.closed` с `sla_met` | Рост и удержание на целевом уровне |
| Потерянные заказы | Заказы без следующего события | Снижение до нуля известных потерь |
| Стоимость обработки одного обращения | Часы поддержки / число тикетов | Снижение на 20–30% |

## 4. Что логируем и трассируем в первую очередь

Команда не может одновременно покрыть все системы, поэтому rollout идёт волнами. Логирование и трейсинг внедряются вместе: у них общий `trace_id`, и это даёт сквозную картину.

| Волна | Системы | Почему именно они |
|---|---|---|
| **1. Заказный контур** (0–1 месяц) | Shop API, CRM API, MES API, RabbitMQ | Здесь теряются и зависают заказы, здесь прямые потери выручки. Покрытие этих четырёх систем даёт максимум эффекта на единицу усилий |
| **2. Пользовательский и контур данных** (1–2 месяца) | Frontend магазина, CRM, MES; PostgreSQL (slow query, ошибки, блокировки); S3 access-логи | Объясняет проблемы, которые видны пользователю, и деградацию БД/хранилища |
| **3. Инфраструктура** (2–3 месяца) | EC2, балансировщик, CI/CD, backup-задачи | Нужна для эксплуатации, но реже помогает в разборе конкретного заказа |

Принцип: сначала системы, через которые проходит каждый заказ и где вероятность потери максимальна; затем — источники пользовательских симптомов; затем — инфраструктура.

## 5. Предлагаемое решение

### 5.1. Технологии и компоненты

| Компонент | Роль |
|---|---|
| **Fluent Bit** | Агент на каждом EC2: читает файлы приложений и системные логи, добавляет метаданные, отправляет дальше |
| **OpenTelemetry Collector** | Единый gateway: приём логов и трейсов, батчинг, обогащение, фильтрация, redaction, маршрутизация |
| **Grafana Loki** | Хранение и поиск логов по меткам, язык запросов LogQL, сжатие и retention |
| **Grafana** | Единый UI: поиск по логам, дашборды, Grafana Alerting, корреляция с трейсами Jaeger |
| **S3** | Объектное хранилище для чанков и индекса Loki; долгосрочный архив |

Поток: `приложения → Fluent Bit → OTel Collector → Loki → Grafana`. Grafana одновременно является UI для логов и для трейсов из задания 3, поэтому поиск идёт в одном окне: по `trace_id` можно перейти из лога в трейс и обратно.

### 5.2. Что дорабатываем

- **Приложения:** переход на структурный JSON (Logback для Spring Boot, Serilog для C#, OTel/pino для фронтендов); единые имена полей; добавление `trace_id`, `span_id`, `order.id` в MDC/контекст; запрет конкатенации строк в сообщениях.
- **Инфраструктура:** Fluent Bit на каждом EC2, OTel Collector в двух инстансах за балансировщиком, Loki в режиме с S3-бэкендом, Grafana в двух инстансах.
- **Loki:** схема меток и потоков, тенанты `app` / `business` / `audit`, retention через compactor, лимиты на размер записи и количество потоков.
- **Поддержка:** сохранённые запросы Grafana «заказ по номеру», «ошибки за 24 часа», «зависшие статусы», «ошибки интеграций».

**Дисциплина меток Loki.** Loki индексирует только метки, поэтому в метки выносим ограниченный набор: `service`, `environment`, `level`, `channel`. Высококардинальные значения — `order.id`, `order.number`, `trace_id`, `partner.id` — остаются в теле JSON-лога и ищутся через LogQL. Если положить `order.id` в метку, число потоков взорвётся и Loki деградирует.

Схема: [C4-диаграмма сбора логов](C4-логирование.drawio).

### 5.3. Политика безопасности

- **Минимизация данных:** не логируем имена, телефоны, e-mail, адреса, паспортные данные, номера карт, содержимое 3D-файлов, пароли и токены.
- **Псевдонимизация:** `customer_id` и `operator_id` — только хеш с солью; `partner.id` разрешён; IP обрезается до подсети, User-Agent нормализуется.
- **Redaction:** на уровне приложения (маскирование полей) и на Collector (regex-фильтры для карт, токенов, e-mail). Обязательные тесты на отсутствие PII в логах.
- **Доступ:** только через корпоративное SSO/OIDC с MFA. В Grafana роли `Viewer` / `Editor` / `Admin`; доступ к datasource и тенантам (`app`, `business`, `audit`) выдаётся по принципу минимальных привилегий. Поддержка видит бизнес- и заказные логи, разработчики — сервисные, безопасность — `audit`. Запись логов через UI запрещена.
- **Сеть и шифрование:** Loki, Grafana и Collector — во внутренней сети, без публичного входа; доступ через VPN/bastion; TLS для транспорта, шифрование S3 (SSE) и дисков.
- **Аудит:** входы в Grafana, поисковые запросы и изменения конфигурации логируются; `audit`-тенант хранится отдельно и не редактируется.
- **Удаление:** по запросу клиента данные удаляются через Loki Delete API и retention; факт удаления фиксируется.

### 5.4. Политика хранения

- **Потоки вместо индексов:** Loki хранит логи в потоках, определяемых метками, например `{service="shop-api", environment="prod", level="info", channel="b2c"}`. Отдельный индекс на систему не нужен.
- **Тенанты и retention:** `app` — 30 дней (технические логи), `business` — 90 дней (события заказов), `audit` — 365 дней (входы, доступ, изменения). Retention настраивается через compactor; для каждого тенанта свои лимиты.
- **Хранилище:** чанки и TSDB-индекс — в S3; локально на нодах только кеш. S3 lifecycle удаляет объекты после истечения retention.
- **Оценка объёма:** при среднем 10 RPS и ~2 КБ логов на запрос — около 1,7 ГБ/день сырых данных. Loki сжимает их примерно в 10 раз: ~170 МБ/день, с replication factor 2 — ~340 МБ/день. За 30 дней — ~10 ГБ, за 90 дней — ~30 ГБ, audit за год — ~60–120 ГБ. Это значительно дешевле, чем хранить те же логи в поисковом индексе.
- **Разделение окружений:** prod, release, dev — разные тенанты или метка `environment`; dev хранится 7 дней.

### 5.5. От сбора логов к анализу

**Алертинг.** Grafana Alerting работает поверх LogQL-запросов:

- рост 5xx и конкретные шаблоны ошибок:
  `sum(count_over_time({service="shop-api", level="error"} [5m])) > 20`;
- отсутствие логов от сервиса (heartbeat):
  `absent_over_time({service="mes-api"} [5m])`;
- всплеск неудачных логинов:
  `sum(count_over_time({service="crm-api"} |= "auth.login" |= "result=failed" [5m]))`;
- медленные запросы и дедлоки БД:
  `count_over_time({service="postgres"} |= "deadlock" [5m]) > 0`;
- ошибки интеграций и рост `retry_count`.

**Поиск аномалий.** Отдельного ML-модуля в Loki нет, поэтому аномалии ловим через Grafana Alerting и сравнение с baseline:

- запрос A — текущее число `order.created` в минуту;
- запрос B — среднее за последний час;
- условие — `A > 5 × B` (или `A < 0.2 × B`) в течение 2–3 минут.

Пример: обычно 4 создания заказа в минуту, внезапно — 10 000. Алерт уходит дежурному и в безопасность; реакция — проверить партнёра, включить rate-limit/WAF, при необходимости заблокировать ключ. Baseline калибруется 2 недели. Если позже понадобится ML-детекция, её можно включить в Grafana Cloud или добавить отдельный сервис — текущий стек это не блокирует.

## 6. Критерии выбора технологии (дополнительное задание)

| Критерий | ELK (Elasticsearch + Logstash + Kibana) | OpenSearch | Splunk | Grafana Loki |
|---|---|---|---|---|
| **Лицензия и стоимость** | Elastic License 2.0; часть функций платная | Apache License 2.0, без лицензионных платежей | Проприетарная, высокая стоимость по объёму | AGPLv3, бесплатно |
| **Полнотекстовый поиск и аналитика** | Очень сильный | Сильный, совместим с Elasticsearch API | Очень сильный, лучшая аналитика | По меткам + grep по телу; слабее Elastic, но достаточно при структурных логах |
| **Масштабирование и объём** | Горизонтальное, проверено на больших объёмах | Горизонтальное, шардирование и репликация | Горизонтальное, но дорогое | Горизонтальное, чанки в S3, очень дешёвое хранение |
| **Ресурсы и эксплуатация** | Тяжёлый JVM-стек, Logstash требователен | Тяжёлый JVM-стек, но можно managed | Умеренная эксплуатация, высокая цена | Лёгкий, низкие требования к CPU и диску |
| **Алертинг и аномалии** | Есть, часть — в платной версии | Встроенные Alerting и Anomaly Detection | Мощные, включены | Grafana Alerting на LogQL; ML-аномалии только в Grafana Cloud или отдельным сервисом |
| **Интеграция с OTel и трейсингом** | Хорошая | Хорошая | Хорошая, но дорогая | Отличная: единая Grafana для логов и трейсов Jaeger |
| **Вендор-лок и TCO** | Средний | Низкий | Высокий | Низкий |

**Выбор — Grafana Loki + Grafana.** Обоснование:

- **самый низкий TCO:** чанки лежат в S3 и сжимаются примерно в 10 раз; при нашем объёме это ~10 ГБ за 30 дней вместо ~120 ГБ в поисковом индексе;
- **единый UI:** Grafana уже используется для метрик и трейсов (задания 2–3), а Loki подключается как datasource; переход «лог → трейс по `trace_id`» делается в одном окне;
- **LogQL закрывает наши запросы:** поиск по `order.id`, `trace_id`, `partner.id`, фильтры по меткам, алерты и базовое сравнение с baseline;
- **простая эксплуатация:** нет JVM-кластера и шардирования индексов; меньше ресурсов и меньше поводов для инцидентов;
- **лицензия AGPLv3** и отсутствие платежей за объём.

Ограничения Loki, которые мы принимаем:

- полнотекстовый поиск слабее Elasticsearch — компенсируем структурными JSON-логами и продуманными метками;
- нет встроенной ML-детекции аномалий — используем Grafana Alerting и baseline-запросы; при необходимости добавим Grafana Cloud ML;
- «дорогие» агрегации по очень большим периодам выполняются медленнее — ограничиваем их дашбордами и retention.

Splunk лучше по аналитике, но слишком дорог для компании такого размера. ELK и OpenSearch близки по возможностям, но требуют тяжёлого JVM-кластера и дорогого хранения. Loki проигрывает им в полнотекстовом поиске, но выигрывает по стоимости и интеграции с уже выбранным стеком Grafana.
