# Архитектурное решение по трейсингу

## 1. Система и C4-диаграмма в контексте трейсинга

Заказ проходит через несколько независимых приложений и два вида транспорта — HTTP и RabbitMQ. Единого идентификатора, по которому можно собрать весь путь заказа, сейчас нет: каждая система пишет свои логи, а о проблеме команда узнаёт из жалобы клиента или партнёра.

### 1.1. Где заказ может «сломаться» или зависнуть

| # | Участок | Что может пойти не так |
|---|---|---|
| 1 | Браузер → Онлайн-магазин → Shop API | JS-ошибка, недоступность API, ошибка валидации, обрыв при загрузке 3D-модели |
| 2 | Shop API → S3 | Загрузка модели не завершилась, S3 вернул ошибку или таймаут |
| 3 | Shop API → Shop DB | Медленный запрос, блокировка, ошибка записи заказа |
| 4 | Shop DB → CRM API | CRM не забрал заказ из общей БД; заказ создан, но не передан дальше |
| 5 | CRM API: подтверждение и смена статуса | Заказ подтверждён вручную, но статус не изменился; ошибка CRM API |
| 6 | CRM API → RabbitMQ | Событие не опубликовано или опубликовано без подтверждения — потеряно |
| 7 | RabbitMQ → MES API | Сообщение в DLQ, нет потребителя, повторные доставки, дубли |
| 8 | MES API: расчёт цены | Расчёт идёт 2–3 минуты (до 30), таймаут, очередь расчётов, зависание воркера |
| 9 | MES API → MES DB | Медленные запросы, блокировки, переполнение соединений |
| 10 | MES API → S3 | Не удалось прочитать 3D-модель для расчёта или производства |
| 11 | MES API → RabbitMQ → CRM API | Событие статуса производства потеряно или обработано дважды |
| 12 | API-партнёр → MES API | Прямой вызов внутреннего API: дубль заказа, потеря, отказ без понятной причины |
| 13 | CRM API → Онлайн-магазин / клиент | Статус не дошёл до клиента, уведомление не отправлено |
| 14 | Фронтенды CRM и MES | Медленный дашборд MES, ошибка интерфейса, зависание 3D-редактора |

### 1.2. Системы, которые нужно покрыть трейсингом

На C4-диаграмме они выделены **красной пунктирной рамкой**:

- **Онлайн-магазин, CRM, MES (фронтенды)** — пользовательский шаг, ошибки JS и время загрузки;
- **Shop API, CRM API, MES API** — обработка HTTP-запросов, работа с БД и S3, публикация и потребление событий;
- **RabbitMQ** — передача контекста трейса в заголовках сообщений;
- **S3 и PostgreSQL** — не инструментируются самостоятельно, но попадают в трейс как клиентские спаны сервисов (обращения к БД и хранилищу);
- **API-партнёры** — на входе создаётся новый трейс, если партнёр не передал `traceparent`.

Не покрываются напрямую: внутренности managed PostgreSQL, S3 и Яндекс Метрики — у них нет собственных спанов, виден только клиентский вызов.

Схема: [C4-диаграмма с трейсингом](C4-трейсинг.drawio).

## 2. Данные, которые должны попадать в трейсинг

Каждый спан должен позволять ответить на вопросы: «что произошло», «где», «когда», «сколько длилось», «успешно ли» и «к какому заказу относится».

| Группа | Поля |
|---|---|
| Идентификация трейса | `trace_id`, `span_id`, `parent_span_id`, `trace_state`, `sampled` |
| Сервис | `service.name`, `service.version`, `deployment.environment` (dev/release/prod), `service.instance.id` |
| Операция | `span.name`, `span.kind` (server/client/producer/consumer/internal), `span.status` (OK/ERROR), `status.message` |
| Время | `start_time`, `end_time`, `duration_ms` |
| HTTP | `http.method`, `http.route` (шаблон, без ID), `http.status_code`, `url.path`, `server.address`, `user_agent` |
| Сообщения | `messaging.system` (rabbitmq), `messaging.destination`, `messaging.operation` (publish/receive/process), `messaging.message_id`, `messaging.conversation_id`, `messaging.redelivered` |
| Заказ | `order.id` (внутренний), `order.number`, `order.status`, `order.previous_status`, `order.channel` (b2c/b2b), `order.stage`, `order.created_at` |
| Партнёр и клиент | `partner.id` или `partner.tier`, `client.type`, `session.id` (для фронтенда, без PII) |
| Расчёт цены | `price.model_complexity`, `price.calculation_id`, `price.queue_wait_ms`, `price.attempt` |
| 3D-модель | `file.id`, `file.size_bytes`, `file.content_type`, `storage.bucket`, `storage.operation` |
| База данных | `db.system` (postgresql), `db.operation` (select/insert/update), `db.sql.table`, `db.rows_affected`, `db.connection_pool.wait_ms` (без текста SQL и параметров) |
| Ошибка | `error.type`, `error.message` (без PII), `error.stack` (только для внутренних сервисов), `exception.escaped` |
| Инфраструктура | `cloud.provider`, `cloud.region`, `host.name`, `k8s.pod.name` (если применимо) |

Обязательные бизнес-атрибуты для спанов конвейера: `order.id`, `order.status`, `order.channel`, `partner.id`/`partner.tier`. Без них трейс остаётся техническим и не отвечает на вопрос «где мой заказ».

## 3. Мотивация

Сейчас путь заказа разорван между тремя приложениями, двумя БД и RabbitMQ. Команда не может быстро ответить: заказ создан? передан в CRM? посчитана ли цена? опубликовано ли событие? Трейсинг собирает весь путь в один `trace_id` и показывает, на каком шаге и сколько времени заказ провёл.

### 3.1. Что это даёт компании

- **Локализация зависших заказов за минуты.** Вместо ручного сопоставления логов трёх систем — один трейс с хронологией и длительностью каждого шага.
- **Обнаружение потерь на стыках.** Видно, что заказ создан, но событие не опубликовано, или сообщение ушло в DLQ, или MES не получил его.
- **Снижение MTTR.** Инженер сразу видит сервис, операцию и ошибку, а не перебирает гипотезы.
- **Обоснование изменений.** Трейсы дают фактические p95/p99 по стадиям, а не оценки; после доработок видно эффект.
- **Меньше ручной поддержки.** Поддержка отвечает на вопросы по заказу через поиск по `order.id`/`trace_id`, не привлекая разработчиков.
- **Готовность к API-партнёрам.** Появляется доказательная база по SLA и причинам отказов для каждого партнёра.

### 3.2. Метрики, на которые повлияет внедрение

**Технические:**

| Метрика | Как измеряем | Целевой эффект |
|---|---|---|
| MTTR (среднее время восстановления) | Время от алерта до закрытия инцидента | Снижение на 30–50% за счёт быстрой локализации |
| Доля заказов с полным трейсом | Заказы, у которых есть спаны всех стадий, / все заказы | ≥ 95% в prod |
| p95 времени обработки заказа по стадиям | Длительность спанов `order.*` | Видимость «тяжёлых» стадий, снижение p95 после оптимизаций |
| Доля ошибок, локализованных по трейсу | Ошибки с указанным сервисом и операцией | ≥ 90% инцидентов без ручного поиска по логам |

**Бизнес-метрики:**

| Метрика | Как измеряем | Целевой эффект |
|---|---|---|
| SLA: доля заказов, закрытых за 3 недели | `order_cycle_time` из трейсов | Рост и удержание на целевом уровне 95% |
| Количество потерянных заказов | Заказы без следующего события в цепочке | Снижение до нуля известных потерь |
| Время заказа в статусе | Длительность стадий из спанов | Сокращение простоев в «непонятных» статусах |
| Стоимость поддержки на заказ | Число обращений и ручных проверок | Снижение за счёт самостоятельного поиска статуса |

## 4. Предлагаемое решение

### 4.1. Технологии

- **OpenTelemetry (OTel)** — единый стандарт сбора и передачи трейсов: SDK для Java, .NET, JavaScript, протокол OTLP.
- **OpenTelemetry Collector** — центральный приёмник: батчинг, ретраи, фильтрация, обогащение, экспорт в хранилище и в span metrics.
- **Jaeger** — хранение, поиск и UI трейсов (совместим с OTLP).
- **W3C Trace Context** — `traceparent`/`tracestate` для сквозной передачи контекста.
- Для второго этапа: **Prometheus + Alertmanager + Grafana** — метрики из трейсов, SLO и алертинг.

### 4.2. Что внедряем и дорабатываем

| Компонент | Изменение |
|---|---|
| Shop API (Spring Boot) | OTel Java Agent или Micrometer Tracing + OTLP-экспорт; ручные спаны на создание заказа, загрузку в S3, публикацию события |
| CRM API (Spring Boot) | То же; спаны на подтверждение заказа, смену статуса, публикацию/потребление RabbitMQ |
| MES API (C#) | OpenTelemetry .NET SDK; спаны на приём заказа, расчёт цены, работу с MES DB и S3, публикацию статусов |
| Фронтенды (Vue, React) | OTel JS SDK: спаны на пользовательские действия, загрузку 3D-редактора, HTTP-вызовы; `traceparent` в запросах к API |
| RabbitMQ | Прокидывание `traceparent` в заголовках сообщений; спаны producer/consumer в сервисах |
| Общие библиотеки | Единый модуль настройки OTel, чтобы не дублировать конфигурацию в каждом сервисе |
| Инфраструктура | OpenTelemetry Collector (2 инстанса за балансировщиком), Jaeger с внешним хранилищем (Elasticsearch/OpenSearch или Cassandra), retention 14 дней |
| API-партнёры | На входе в MES API создаётся корневой спан; если партнёр прислал `traceparent` — контекст продолжается |

### 4.3. Как устроен трейс заказа

1. Пользователь или партнёр инициирует запрос — создаётся корневой спан `order.create` (или `order.receive` для B2B).
2. Shop API создаёт спан `order.persist`, дочерние спаны `s3.upload` и `db.insert`.
3. CRM API при обработке заказа создаёт спан `order.confirm` и `order.status.change`.
4. При публикации события создаётся спан `rabbitmq.publish`, `traceparent` кладётся в заголовки сообщения.
5. MES API при получении сообщения создаёт спан `rabbitmq.process` с тем же `trace_id`, далее `price.calculate`, `db.update`, `rabbitmq.publish`.
6. Все спаны одного заказа связываются атрибутом `order.id`; в Jaeger можно найти трейс по `order.id` или `trace_id`.

Для асинхронных сообщений используется **контекст сообщения**, а не только HTTP-заголовки: без этого трейс обрывается на границе RabbitMQ.

[C4-диаграмма с трейсингом](C4-трейсинг.drawio): красным выделены новые компоненты (OpenTelemetry Collector, Jaeger), новые связи (OTLP от сервисов, экспорт трейсов) и системы, покрываемые трейсингом (красная пунктирная рамка).

## 5. Компромиссы

| Ситуация | Почему трейсинг не даст эффекта или дорог |
|---|---|
| Проприетарная система без возможности инструментирования | MES куплен с исходным кодом, поэтому в теории дорабатываем; если бы исходников не было, пришлось бы довольствоваться логами и внешними спанами. Стоимость доработки может быть неоправданно высокой |
| Полная выборка 100% трейсов | Дорого по CPU, сети и хранилищу. Используем sampling: 100% ошибок и медленных запросов, 5–10% успешных; для разбора редких инцидентов — tail sampling |
| Нет контекста в старых/внешних компонентах | Трейс обрывается на границе; приходится вручную связывать по `order.id`, что снижает автоматизацию |
| Очень короткие или очень долгие операции | Короткие спаны дают шум; для долгих (расчёт цены) нужен отдельный учёт и таймауты, иначе трейс «висит» и не завершается |
| Проблема не в коде, а в инфраструктуре | Переполнение диска, сеть, отказ managed-сервиса видны в метриках, а не в трейсах; трейсинг дополняет мониторинг, но не заменяет его |
| Затраты на хранение | Большой объём спанов требует денег на хранилище и эксплуатацию; нужен retention и downsampling |
| Ошибки в семплировании | Редкий дефект может не попасть в выборку; поэтому ошибки и аномалии семплируются отдельно |
| Отсутствие дисциплины атрибутов | Если `order.id` не передаётся, трейсы не связываются с бизнес-событиями; нужны соглашения и code review |

Трейсинг окупается на системе с распределённым заказом, но не заменяет метрики, алерты и логи: это три разных инструмента.

## 6. Безопасность

- **Аутентификация:** доступ к Jaeger и Grafana — только через корпоративный SSO (Keycloak/Active Directory), отдельные учётные записи, MFA.
- **Авторизация:** роли `Support` (просмотр трейсов по заказу), `Developer` (полный поиск), `On-call` (алерты и дашборды), `Admin` (настройка). Принцип минимальных привилегий.
- **Сетевой доступ:** Collector и Jaeger развёрнуты во внутренней сети, без публичного ingress; доступ — через VPN или bastion. OTLP-порт принимает трафик только от сервисов кластера.
- **Шифрование:** TLS для OTLP (gRPC/HTTP), TLS к хранилищу трейсов, шифрование данных на диске.
- **Защита от PII:** в спаны не передаются имена, телефоны, e-mail, адреса и содержимое 3D-файлов. `partner.id` и `user.id` передаются в псевдонимизированном виде; текст ошибок фильтруется.
- **Ограничение объёма:** rate-limit на Collector, максимальный размер атрибутов, запрет произвольных заголовков; защита от «шумного» клиента.
- **Хранение и удаление:** retention 14 дней, автоматическое удаление; доступ к старым трейсам — по запросу с аудитом.
- **Аудит:** логирование доступа к трейсам и изменений конфигурации; алерты на подозрительную активность.
- **Валидация входа:** проверка OTLP-запросов, лимиты на количество спанов и атрибутов, защита от подмены `service.name`.

## 7. Автоматический мониторинг и алертинг на данных трейсинга (дополнительное задание)

### 7.1. Как получаем метрики из трейсов

В OpenTelemetry Collector включается **span metrics connector**: он агрегирует спаны в метрики (count, duration, errors) по измерениям `service`, `operation`, `status`, `order.channel`, `order.status`. Далее:

`сервисы → OTel Collector → span metrics → Prometheus → Alertmanager → Grafana`

Дополнительно Jaeger отдаёт трейсы в Grafana для перехода «алерт → конкретный трейс».

### 7.2. Какие метрики и алерты строим

| Метрика из трейсов | Алерт | Условие |
|---|---|---|
| `order_cycle_time` (полное время заказа) | Нарушение SLA | p95 > 21 день или доля в SLA < 95% |
| `order_stage_duration` по статусам | Заказ завис в статусе | Время в статусе > нормы для стадии |
| `order_pipeline_errors` | Ошибка на стадии | Рост ошибок > 1% за 5 минут |
| `order_missing_next_event` | Разрыв конвейера | Заказ без следующего события > N минут |
| `rabbitmq_process_duration` / `redelivered` | Затор или дубли | p95 > порога, рост redelivered |
| `price_calculation_duration` | Долгий расчёт | p95 > 5 минут, p99 > 15 минут |
| `trace_completeness` | Потеря трейсов | Доля заказов с полным трейсом < 95% |

Алерты маршрутизируются в Alertmanager: P1 — звонок дежурному, P2 — сообщение в канал и тикет, P3 — дашборд. К каждому алерту прикладывается ссылка на трейс и `order.id`, чтобы разбор начинался сразу с места проблемы.
