# Планирование: анализ, идентификация проблем и поиск решений

## 1. Анализ текущей архитектуры

Система состоит из трёх приложений:

- **Онлайн-магазин** — Vue + Java Spring Boot, своя **Shop DB** (PostgreSQL).
- **CRM** — Vue + Java Spring Boot; по схеме C4 CRM API работает **с той же Shop DB**, отдельной БД у CRM нет.
- **MES** — React + C#; своя **MES DB** (PostgreSQL). MES куплен вместе с исходным кодом, расчёт стоимости изделия выполняется на его стороне и занимает 2–3 минуты (до 30 минут на сложных моделях).

Связи между системами:

- **CRM ⇄ MES** — через RabbitMQ. Это единственный интеграционный контур между ними; реализован командой «Александрита».
- **Shop API не подключён к RabbitMQ.** Заказ B2C-клиента попадает в общую Shop DB, откуда его забирает CRM API и публикует события для MES. То есть магазин и производство связаны косвенно, через CRM и общую БД.
- **Внешние API-пользователи (сторонние продавцы) обращаются напрямую в MES API.** В этом сценарии заказ создаётся в CRM по сообщению из очереди от MES.
- **3D-файлы** хранятся в общем S3-хранилище; их читают Shop API, MES API и CRM API.

Инфраструктура и процессы:

- Три окружения: dev, release, prod. Всё в облаке: **по одному EC2-инстансу на приложение**, БД — managed PostgreSQL **в одном инстансе на чтение и запись** (реплик нет).
- CI/CD: dev — автодеплой после merge PR и юнит-тестов; release и prod — **ручной деплой**.
- Команда — 8 инженеров; спринты по 2 недели; QA прогоняет E2E **вручную**; баги high/highest блокируют релиз.

Ключевой вывод анализа: производственные мощности загружены не полностью и выдерживают двукратный рост, поэтому причины просрочек и потерь заказов находятся **в цифровом конвейере заказа и интеграциях**, а не в производстве.

## 2. Проблемные места

| № | Проблема | Признак в кейсе | Тип |
|---|---|---|---|
| П1 | Заказ «зависает» в цифровом конвейере на месяцы вместо обещанных 3 недель | Жалобы B2C и партнёров; производство при этом не загружено | существующая |
| П2 | Заказы теряются / не создаются | Ежедневные жалобы API-пользователей «не получили заказ»; потеря крупных контрактов | существующая |
| П3 | Синхронный расчёт цены в критическом пути заказа | Расчёт 2–3 мин (до 30 мин), выполняется на одном инстансе MES; после открытия API очередь расчётов забита | существующая |
| П4 | Публичным API является сам внутренний MES API | Нет шлюза, лимитов, квот, контрактов; флуд внешних заказов деградирует внутренние процессы | существующая |
| П5 | Медленная первая страница MES (дашборд оператора) | Фильтр по статусам и пагинация не помогли; операторам важны самые новые заказы (от них зависит вознаграждение) | существующая |
| П6 | Общая Shop DB у магазина и CRM API | Нет владельца данных, конфликты схем, риск блокировок, системы нельзя развивать независимо | существующая |
| П7 | Единичные инстансы и единые точки отказа | По одному EC2 на приложение, БД без реплик, один RabbitMQ; нет запаса под рост +100 заказов/мес | существующая |
| П8 | Нет наблюдаемости конвейера заказа | Нет метрик времени в статусе, глубины очередей, алертов; о проблемах узнают из жалоб | существующая |
| П9 | Нет явного state machine и единого источника правды по статусу | Статусы распределены по трём системам и двум БД; непонятно, где заказ застрял | существующая |
| П10 | Деградация процесса релиза | Ручной E2E, блокировка релиза багами high/highest; задержки выросли до нескольких месяцев | существующая |
| П11 | Нет rate-limit/квот/контракта для публичного API | При подключении новых партнёров флуд будет расти, SLA гарантировать нельзя | потенциальная |
| П12 | Нет честного/автоматического распределения заказов между операторами | Ручное «кто успел — тот взял»; новые заказы могут залёживаться | потенциальная |
| П13 | Bus factor по MES (C#) | MES знают один разработчик и тимлид; остальная команда — Java/Vue | потенциальная |
| П14 | Клиент не видит актуальный статус заказа | Обновления попадают в магазин косвенно; растёт нагрузка на поддержку | потенциальная |

## 3. Инициативы

| № | Инициатива | Содержание | Закрывает | Объём |
|---|---|---|---|---|
| И1 | Надёжный событийный конвейер | Outbox в сервисах-источниках событий, DLQ и ретраи, идемпотентные потребители, версионированные контракты событий, мониторинг очередей | П2, П8 | M |
| И2 | State machine заказа и SLA-таймеры | Единый владелец статуса, формальные переходы, таймеры «время в статусе», алерты и эскалация по зависшим заказам | П1, П9 | M |
| И3 | Асинхронный масштабируемый расчёт цены | Очередь заявок на расчёт, пул параллельных воркеров MES с autoscaling, результат событием `price.calculated`, SLA по времени расчёта | П1, П3 | L |
| И4 | Ускорение дашборда MES | Композитный индекс `(status, created_at)`, keyset-пагинация, оптимизация агрегатов, real-time обновление через WebSocket, сортировка «новые сверху» | П5, П12 | S |
| И5 | Выделенный публичный API | API Gateway с ключами, rate-limit, квотами и идемпотентностью; отдельный сервис приёма партнёрских заказов, внутренние системы не экспонируются | П4, П11 | L |
| И6 | Масштабирование инфраструктуры и БД | LB + несколько инстансов с autoscaling, read-реплики PostgreSQL, разделение общей Shop DB магазина и CRM, HA RabbitMQ | П6, П7 | L |
| И7 | Наблюдаемость и SLO | Структурированные логи, трейсинг, метрики заказов и очередей, дашборды, алерты, SLO | П8 | M |
| И8 | Прозрачность статуса для клиентов | Актуальный статус в личном кабинете, уведомления, вебхуки для API-партнёров | П14 | S–M |
| И9 | Улучшение CI/CD и релиза | Автотесты (включая E2E критических сценариев), feature-флаги, канареечные деплои, сокращение блокировок релиза | П10 | M |
| И10 | Команда и знания | Найм backend и DevOps, обучение событийным паттернам, снятие bus factor по MES, владелец API-продукта | П13, П4 | S |

## 4. Приоритизация и ход рассуждений

Критерии приоритета:
1. **Бизнес-эффект** — насколько быстро снижаются жалобы и возвращаются контракты.
2. **Срочность** — насколько проблема уже «кровоточит».
3. **Базовость** — является ли инициатива предпосылкой для остальных.
4. **Реализуемость** — посильна ли она команде из 8 человек в двухнедельных спринтах.

Порядок приоритета:

1. **И1 — надёжный событийный конвейер.** Напрямую устраняет потерю заказов (П2) — главную причину потери контрактов. Это фундамент: без outbox/DLQ/идемпотентности остальные инициативы не дадут гарантий.
2. **И2 — state machine и SLA-таймеры.** Даёт ответ, где именно застревают заказы, и позволяет гарантировать срок (П1, П9). Опирается на достоверные события из И1.
3. **И4 — быстрый дашборд операторов.** Малая стоимость, независимость, немедленный эффект для операторов; снимает самый громкий симптом (П5). Выполняется параллельно как быстрая победа.
4. **И3 — асинхронный масштабируемый расчёт цены.** Снимает главное узкое место конвейера (П3) — наиболее вероятную причину «месяцев» задержки. Крупная инициатива, поэтому сразу после быстрых побед.
5. **И7 — наблюдаемость и SLO.** Закрепляет результат И2/И3, снижает время диагностики (П8).
6. **И5 — выделенный публичный API.** Изолирует внешний контур (П4, П11). Логично после стабилизации конвейера, иначе шлюз будет пропускать трафик через тот же сломанный конвейер.
7. **И6 — масштабирование инфраструктуры и БД.** Снимает единичные точки отказа и разделяет общую БД (П6, П7); частично идёт параллельно с И3 (нужен autoscaling воркеров).
8. **И8 — прозрачность статуса для клиентов.** Снижает поток жалоб (П14), выполняется после И1/И2.
9. **И9 — CI/CD и процесс релиза.** Убирает растущие задержки релизов (П10); важно для скорости всех изменений.
10. **И10 — команда и знания.** Организационная поддержка всех инициатив (П13).

Рекомендуемые волны:
- **0–2 месяца:** И1, И2, И4.
- **2–5 месяцев:** И3, И7.
- **4–6+ месяцев:** И5, И6, начало И8.
- **Постоянно:** И9, И10.

## 5. Ответы на вопросы задания

### 5.1. Целевая архитектура через полгода

Принципы:
- асинхронность по умолчанию: долгие операции (расчёт цены, производственные статусы) — только через события;
- надёжный обмен: outbox, DLQ, ретраи, идемпотентность, версионированные контракты;
- единый агрегат «Заказ» с явным state machine и SLA по стадиям;
- изолированный внешний контур: партнёры работают через API-шлюз, внутренние системы наружу не открыты;
- горизонтальное масштабирование и отказоустойчивость;
- наблюдаемость и SLO.

Целевая схема приведена в файле `Task1/Целевая архитектура.drawio` (формат draw.io).

Краткое описание ключевых элементов:
- **B2B API Gateway** изолирует партнёрский контур: ключи, rate-limit, квоты, идемпотентность.
- **Надёжная шина событий** (RabbitMQ + DLQ): outbox, идемпотентные потребители, версионированные контракты событий; события заказа: `order.created → order.submitted → price.calculated → order.approved → manufacturing.* → order.shipped → order.closed`.
- **Pricing workers** — параллельный масштабируемый расчёт цены; результат публикуется событием `price.calculated`.
- **Разделение БД**: у магазина — Shop DB, у CRM — CRM/Order DB (единый агрегат «Заказ» и статусы), у MES — MES DB; 3D-файлы — общий S3.
- **Инфраструктура**: LB + autoscaling EC2, PostgreSQL с read-репликами, HA RabbitMQ, наблюдаемость (метрики, трейсинг, алерты, SLO).

Что меняется относительно текущего состояния:

| Аспект | Сейчас | Через полгода |
|---|---|---|
| Интеграция CRM↔MES | RabbitMQ без гарантий доставки | Outbox + DLQ + ретраи + идемпотентность + контракты |
| Статус заказа | Три системы, две БД, без владельца | Единый агрегат, state machine, SLA-таймеры |
| Расчёт цены | Синхронно, последовательно, один инстанс | Асинхронно, параллельно, масштабируемый пул воркеров |
| Публичный API | Внутренний MES API | B2B API Gateway + сервис приёма заказов |
| Дашборд операторов | Медленный, фильтр и пагинация | Индексы, keyset, real-time, «новые сверху» |
| Наблюдаемость | Отсутствует | Метрики, трейсинг, алерты, SLO |
| Инфраструктура | 1 EC2 на сервис, БД без реплик, общая БД | Несколько инстансов + LB, реплики, разделение БД |

За горизонт 6 месяцев сознательно выносятся: полный переход на микросервисы, автоматическое распределение заказов между операторами и мультирегиональная отказоустойчивость — команде из 8 человек это не потянуть одновременно с устранением текущих потерь.

### 5.2. Если бы можно было выполнить только три пункта

Выбрал бы:

1. **И1 — надёжный событийный конвейер.** Останавливает потерю заказов — самую дорогую проблему (уже потеряны крупные контракты) и техническую предпосылку для всех остальных инициатив.
2. **И2 — state machine заказа и SLA-таймеры.** Превращает «заказ делается месяцами» из неизвестности в измеримую проблему: видно, на какой стадии и сколько заказ стоит, есть алерты и эскалация. Без этого мы не сможем ни гарантировать срок, ни проверить эффект остальных изменений.
3. **И3 — асинхронный масштабируемый расчёт цены.** Убирает главный затор конвейера: медленный последовательный расчёт на одном инстансе. Именно он объясняет, почему при свободном производстве заказы стоят месяцами, и почему после открытия API ситуация ухудшилась.

Связка: **И1** гарантирует доставку событий → **И2** показывает, что и где происходит → **И3** устраняет затор. Вместе они закрывают обе главные жалобы: «не получил заказ» и «заказ делается месяцами».

Формально в тройку не включаю И4 (быстрый дашборд) — но это локальная задача малого объёма, которую я бы выполнял параллельно в первые недели как быструю победу. Также не включаю И5: вводить контрактный контур для API бессмысленно, пока сам конвейер теряет заказы.

## 6. Команда и найм

Существующей команды из 8 человек достаточно для запуска И1, И2 и И4, но для реализации всего плана в 6 месяцев потребуется усиление:

- **Backend-разработчик (Java или C#)** — снять bus factor по MES и ускорить И3/И5.
- **DevOps-инженер** (усиление) — autoscaling, read-реплики, HA RabbitMQ, наблюдаемость (И6, И7).
- **Владелец API-продукта** — контракты, SLA и коммуникация с партнёрами (И5).
- Обучение команды событийным паттернам (outbox, DLQ, идемпотентность) — обязательно, иначе И1/И2/И3 лягут на одного-двух человек.
